# 《抽卡修仙传》开发前最终架构审计 · v0.5

> 审计日期：2026-10-19 · 范围：最新 GDD、解锁、经济、遗物、系统归属、机器图鉴、校验脚本、GitHub Pages 旧原型。  
> **结论：有条件 GO（可以开始 M0 / M1 核心开发），不等于数值平衡完成或已达到可发布状态。**  
> 本轮只修设计文件、数据配置、图鉴查看器与验证脚本；**没有改在线游戏玩法**。

## 1. 最终结论（先看）

**骨架是否完善？** 是，作为轻量修仙增量肉鸽的工程骨架基本完善：战斗探索→稳定资源→多系统养成→境界突破→轮回→全局遗物→下一世，主次分明；未来内容的接入点有清晰边界。

**扩展其他系统是否方便？** 经过本次补丁后，已具备可扩展的区块：稳定ID、账号与当世数据分层、唯一实体所有权、统一奖品派发、EffectResolver、独立关卡注册表、可重复评估的解锁依赖、版本化图鉴与数据自动验证。增加宗门、灵根、命格、道侣等新系统不必重写战斗内核；但其专属成长玩法仍需设计，不能靠往配置填数字就完成。

**现在能不能施工？** 可以从 **M0 游戏规则/数据引擎** 开始，并沿 M1→M3 做首世与第二世纵向切片。**不能直接把 v0.5 文档等同于已平衡的最终产品PRD，更不应该一次性批量生成150层与所有系统。**

## 2. 发现并已修复的关键问题

## 4. 未来添加系统的架构自检

以下场景应当可以**在不修改战斗结算核心代码**的前提下扩展：

| 扩展 | 只需要新增/修改 | 不能做 |
|---|---|---|
| 新功法、宠物、建筑 | 配置定义、合法效果Key（如果已存在可不新增）、对应图鉴/资源处理 | 在UI写英雄攻击+30 |
| 新地图/敌人 | ZoneDef、StageDef、EnemyDef、关卡首次解锁 | 硬编码“地图编号×30”或修改全部旧地图编号 |
| 宗门养成 | 宗门状态域、培养/升级命令、宗门卡包（若需要）、效果与解锁 | 把宗门值直接写进洞府或功法对象 |
| 道侣系统 | 道侣独立养成对象、奖励结算、出战/辅助贡献声明 | 把道侣强行复用灵宠唯一实体结构 |
| 命格/天赋 | 按是否永久明确放在Run或Meta、注册效果类型 | 悄悄增加一套与遗物相同的永久倍率却没有上限 |
| 新品质/新天命箱 | 新版Schema、赔率与显示、迁移、抽卡模拟 | 直接改现有五阶权重而不验证保底和毕业规则 |

“可扩展”是数据和依赖方向已经规划正确，而非新功能完全不需要编写新代码。新增 subsystem 必须满足：**独立玩法价值、唯一资产存储、版本化ID、效果归属、开关解锁、存档与测试**。

## 5. 仍未解决、但不阻止 M0 开发的风险

### A. 战斗成长的真实乐趣，需实际原型验证

战斗数值引擎尚未按 v0.5 实装，现有玩法还无法证明三属性的策略差异。必须模拟攻/血/防对高血、高攻、高防敌人的差异、出战灵宠贡献，并测试首30层至少三种可行养成路线。

**阻止进入 M2 的条件**：打Boss依旧只能看“综合战力够不够”，或者只升级攻击长期总是最优。

### B. 正式数值尚未收敛

目前基础关卡样例只覆盖青云普通1–30，不是“可直接上线的30关数值”。还缺从角色初始属性、修为升级成本、灵石训练费用、卡包价格/抽取频率、每分钟扫荡收益到Boss通关时间的**共同平衡模型**。

**阻止进入公开测试的条件**：常规玩家遭遇无法靠稳定修炼修复的资源死锁；或轮回前30层最优策略是无限等待。

### C. 超低鸿蒙概率的现实追求时间

0.01%意味着首次中奖期望约10,000箱，**不是第10,000箱保底**。即使深层单世按候选曲线约32箱估算，理论期望也需约313次相同深度轮回才第一次出现。四件全部拥有的期望约40,000箱，是数百乃至数千小时级目标，不能作为常规玩家的内容解锁条件。

**阻止正式发行的条件**：宣传暗示短期可出鸿蒙、暗藏提高掉率机制、正常主线敌人按鸿蒙加成账号设置难度。

### D. 新版本永久解锁的存档升级

必须在每次更新后依据账号最高合法普通主线进度与真实突破/轮回记录重新计算已满足的新功能，而非只监听新产生的关卡事件；否则老玩家在新版本可能无法获得P1内容。

**阻止版本升级的条件**：已到第60层的旧存档无法开启新上线的法宝模块。

### E. 移动端质量、发行形态与广告

目前项目仍是静态Pages老原型。决定正式上架渠道前，需核对TapTap小游戏与APK的SDK/广告/存档实际差异。内容设计预留激励视频接口，但不能宣称完成商业化接入。正式视觉、音效、无障碍点击范围和长时间运行性能尚需实际浏览器与手机测试。

## 6. 数据/测试质量门槛

### 已完成的静态验证

- 30常规 + 4鸿蒙：ID唯一、品质、数值/叠加上限、注册Key；
- 鸿蒙独立触发概率0.0001、不受常规品质/保底影响、额外奖励且唯一1份；
- 全普通遗物毕业后仍可在有价值时开箱，最终全毕业后关闭空抽；
- 18个解锁节点：前置字段、触发事件、账号创建默认探索、同层多解锁、关联正确的免费包；
- 5个地图定义：主线范围连续、30关样例层数/敌人/区域关联有效；
- 图鉴：JSON与五张派生CSV一致，137个ID唯一。

**静态验证不等于游戏运行验证**。尚没有新的战斗引擎、真实存档升级测试和十万次抽箱实际模拟；不要把 CI 绿色当成“游戏好玩、数值正确”的证明。

### 开发流水线（先M0后M1）

~~~bash
node scripts/validate-codex.mjs
node scripts/sync-codex-v0.5.mjs --check
node scripts/validate-codex-v0.5.mjs
# 施工后还需要新增并让CI自动运行：
npm run typecheck
npm run test
npm run simulate:balance
npm run build
~~~

需要能复现随机种子、支持同seed的十连与10单抽等价验证、同一BattleID或txnId不能发双份奖励、Meta永久资产不随轮回丢失、抽不到鸿蒙仍可打通正常主线。

## 7. 开工审批和执行建议

**结论：M0核心架构和M1玩法纵向切片可以开工；广告/完整百关/全模块大规模施工暂不批准。**

1. **M0**：建立TypeScript业务引擎、游戏状态域、纯函数战斗、概率奖池、静态内容注册、CI、迁移备份。以 [实施契约](IMPLEMENTATION-CONTRACT-v0.5.md) 为唯一代码职责指南。
2. **M1**：青云普通30层、自动推进、卡关扫荡、灵石攻防血训练、首个Boss及突破，校验稳定成长的乐趣。
3. **M2**：功法/洞府/灵宠，从抽包到培养到参战或提高产出完整闭环，至少三种可行策略。
4. **M3**：首轮轮回、因果、遗物与鸿蒙奖池、第二世反馈；确认没有“抽完一次永久成长但仍无事可做”。
5. **M4**：补内容后再开放险境和赤砂地图、记录系统；真实手机试玩并据此调每分钟收益/抽卡频率。

**暂不做UI大美术、长篇剧情、宗门与道侣填充、复杂炼丹材料、联机、强制广告**。这些内容等核心可玩性通过后再扩展。

最终的检验问题仍然是：**即使这5分钟没有抽到任何好卡，玩家是否还因为能战胜新的敌人、提升修为、突破境界，而愿意继续下一世？** 如果成立，整个系统才真正有耐玩性。
