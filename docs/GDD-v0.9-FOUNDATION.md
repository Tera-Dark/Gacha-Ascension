# 《抽卡修仙传》v0.9 · 放置 × 增量 × 抽卡正式骨架

> 2026-10-20 · **目标版本设计 + 已落地框架的真实边界** · [最新独立预览](https://tera-dark.github.io/Gacha-Ascension/preview-v0.8.html)  
> 核心设计不变：**战斗提供资源；除战斗外，一切构筑与养成产出通过抽卡获得**。无数值 Lv 制，炼气→筑基→金丹→元婴→化神，各境初/中/后/圆满共20状态，24个具名地图计划。  
> 这不是「已经通过真人评分9.0」的声明。9.0是下一阶段的**设计验收目标**，目前还没有足够真人数据证明。

## A. 玩家价值：四个时间层级

| 时间层级 | 期待事件 | 必须可以清晰观测 |
|---|---|---|
| 10秒至2分钟 | 下一抽改变攻击、悟道、灵宠或收入 | 抽前抽后比较 / 自动战斗结果 / 下次抽取倒计时 |
| 3–20分钟 | 当前关Boss攻克、功法构筑变化、跨境突破 | 3个不同思路皆可通过、Boss能力有反制 |
| 数小时至数日 | 可积累的离线产出、下一地图与境界、轮回 | 当前目标、收益/分钟、无需重复无效操作 |
| 数周至长期 | 无上限遗物累积与极端稀有收藏 | 常规永不死池、稀有透明概率、永不强制抽到才能通关 |

## B. 参考 Obelisk Miner 的改版遗物结构

参考 [Obelisk Miner Wiki - Chests](https://obeliskminer.fandom.com/wiki/Chests)：其常规Relic依品质分级，存在无限叠加的伤害、经验/出售收益类词条，另有达到上限后退出池子的词条。我们借鉴机制思想，但自行定义阶层、概率、物品和效果。

**当前真正写进配置与引擎的内容：**
- **常规天命箱**：售价40因果、每箱必得1件常规遗物，品质权重黄50%、玄28%、地14%、天7%、仙1%。若目标阶层全满，**只在仍有物品的阶层内按剩余权重重新归一化**。
- **基础无上限类**：凡尘武骨（基础攻击+2/份）、玄黄护符（基础气血+12/份）、聚宝微光（战斗灵石+1%/份）、聚灵仙纹（战斗修为+1%/份），四种无永久等级上限。基础永久增益不受局内卡牌类600%收益硬帽截断；数值进入JavaScript安全整数边界时应明示，待未来大数系统升级。
- **有上限类**：部分稀有战斗、灵宠与资源百分比增益有独立最高份数，满级后不再参与常规抽选。可抽常规池始终存在至少4种无上限遗物，不会出现「集齐基础奖池→无法再抽超级稀有」。
- **普通高品质保障**：目前≥天阶25箱保底、仙阶80箱保底，但仅在对应阶仍存在未满级奖励时生效；不可把毕业后的失效目标伪装为保底。
- **太古奇珍**：在每一箱的基础奖励之外，独立**1/100,000（0.001%）**判定，4件测试型专项极品：主角伤害、灵宠伤害、战斗修为、战斗灵石。唯一拥有、无保底。
- **鸿蒙异宝**：在每一箱的基础奖励之外，独立**1/1,000,000（0.0001%）**判定，保留开天斧、始祖印、洞天珠、大道书4种强大的专项终极遗物；**无保底、不提高概率、不提高箱内品质，也不作为通关门槛**。
- 太古与鸿蒙互为**两个独立追加事件**，数学上单次同箱可同时触发；一件满收集的超稀有不会改变普通遗物的保障与出箱。
- 这些概率适用于**每箱整体的该层级追加机会**，不是单件道具各自百万分之一。先决定是否进入超级池，进入后才从池中未拥有道具选一件。
- 遗物效果严格按乘区分开，鸿蒙开天斧只对主角攻击、始祖印仅作用于宠物、洞天珠只放大洞府增量、大道书只增强功法正面效果；太古专项以同样原则隔离，杜绝互相无限倍乘。
- 测试版常规物品现在14种；24图完整版的最终普通遗物目录仍需持续增补。**并未声称正式30件已经完整落地**。

### 极端稀有的设计底线

百万分之一的首次命中数学期望是1,000,000箱，不是抽到第1,000,000箱就能保证获得。玩家应当将其当成「可观而不可得」的世界级收藏，不应作为图鉴毕业必须完成的主线任务，不应提供付费增幅、不可生成虚假的「马上就能出」提示。正常玩家的主要成就来自大量**常规无上限**成长与跨境突破。

当前使用本地确定性伪随机数，**适合无服务器的个人试玩与自动测试，不适合作为涉及เงินจริง真钱充值的可验证抽奖系统**；真正运营时必须重新设计服务端发奖、权重审计、防刷及监管合规机制。

## C. 放置底座：不可再以点击速度作为收益来源

**已完成**：
- 自动打当前关小怪，失败不回退守卫进度；
- 手动小怪战斗有统一冷却限制，不能无限快速点击刷灵石；
- 已启动挂机的状态落盘，本地关闭/后台后恢复时使用和普通在线战斗相同的敌人、命中、随机奖励算法重算；
- 首世每次离线结算最多15分钟，轮回后最多2小时（**测试期参数**），按照真实战斗次数累计收益，带剩余不足一次战斗的毫秒余数；
- 离线状态**不会**自动挑战守卫、Boss、消耗灵石抽卡、突破境界或轮回；
- 结束挂机前结算未领取的产出；同一时间戳重复领取不重复结算；当前小怪若打不过会停止活动避免离线烧空时间。

**仍需以后完善**：
- UI当前的「每场结算间隔」只是切片压缩时间，尚未与每次战斗内部完整的毫秒耗时100%对齐；下一版要统一整个世界的真实战斗时钟，支持手动与自动共享总耗时、战斗中的暂停/恢复状态。
- 浏览器本地时间可被人为修改，GitHub Pages纯本地模式无能力提供服务器级防作弊；不要宣称这是上线级可靠时钟。
- 大量离线战斗目前可在同一次领取中逐场模拟，今后地图增加时需批量分块和超时保护，避免移动浏览器在长离线中阻塞UI。
- 当前本地存档仍依赖localStorage，用户清空浏览器数据会丢失内容；必须先做安全导入、导出和自动备份，再考虑云账号功能。

## D. 抽卡交互和反馈体系

**已实装的可替换动效骨架：**
- 战力/聚财/修为/功法/洞府/御兽/丹道七个卡包各自有不同视觉语言与动态方式；独立的天命「仪式」动效；
- 充能→揭晓→卡牌陈列→主动收下，黄/玄/地/天/仙/太古/鸿蒙有不同品质层次；十连可展示多张卡；
- 全流程支持跳过与\`prefers-reduced-motion\`，手机纵屏、卡牌网格、单手点击尺寸可用；
- 抽奖结果**先完成原子事务并持久保存，然后才播放外观动画**；跳过、刷新或十连不应重复发奖；
- UI的动效不参与抽卡概率决策。大奖动画完全由已经取得的真实结果驱动，绝不「先演出，再决定掉落」。

**未来可插拔接口**：卡牌插画、专属粒子、飞入效果、道具预览、音效、可配置抽卡时长、重复卡升级演出、隐藏/音量及性能设置。当前只完成CSS/DOM动效架构，未生成最终音频和角色美术。

## E. 各系统职责与可扩展解锁

当前\`src/v8/modules.mjs\`统一定义已实装系统与规划系统、状态归属、产出渠道、支持的EffectKeys、里程碑阈值：
- **跑图**\`RunState\`：地图／当前关／Boss；小怪只产基础货币、修为。
- **培养**\`RunState\`：抽卡获得属性、功法、洞府、灵宠、丹药；随轮回清空。
- **天命**\`MetaState\`：因果与跨世遗物、常规品质保底、太古/鸿蒙记录；跨轮回保留。
- **放置**\`RunState.idle\`：当前小怪目标／上次结算时间／时间尾数；页面与战斗状态不同。
- **预留规划**：法宝、宗门、飞升等注册为\`planned\`，但不能伪装按钮可用或发放尚未完成的卡。
- **解锁里程碑**\`data/v8-slice.json/features.unlockAtGlobalCheckpoint\`：引擎和UI都按同一处数据进行验证。当前为方便试玩**七种卡包阈值都为0，全部开放**；后续重新排序仅更改公开配置和关联引导，不需要拆掉玩法。
- **内容验证**：未知卡牌效果、未知卡包或缺失解锁节点应在数据加载时直接报错，不能悄悄当成一张无效卡。

## F. 「9.0以上」的验收标准，而不是自评宣言

| 维度 | 现阶段改善 | 必须验证后才能评估达到9.0的内容 |
|---|---|---|
| 核心创意 | 修仙境界+所有养成源于抽卡 | 目标用户首次30分钟能清晰说出独特卖点并愿意继续 |
| 新手引导 | 当前四图、直接首抽 | 无教程卡死、30秒内首获有效卡、2分钟内理解刷怪/守卫分工 |
| 战斗策略 | 命中/减伤/流派/Boss多波 | 同一Boss至少3种不依赖超稀有道具的通过路径 |
| 抽卡满足感 | 7类不同动效、正式概率和保底规则 | 高品质揭晓有显著质变、重复卡仍有选择、非连点刷资源 |
| 增量成长 | 无上限常规遗物和长期指数成本 | 每次长线阶段都有可感知效率改善，无属性卡落入永久零收益陷阱 |
| 放置收益 | 在线/安全离线共用真实小怪战斗 | 统一真实时钟、离线与在线结果一致、手机无后台挂机压力 |
| 地图闯关 | 当前关刷怪+三波Boss | 24图逐张具备独立机制与Boss策略，不是统一乘血量 |
| 解锁新鲜感 | 数据驱动底座已完成 | 前密后疏的功能释放曲线，盲测玩家能自然理解新系统 |
| 轮回留存 | 无死池、永久常规成长、二世额外离线上限 | 第二世明显更省操作、地图时间和构筑策略有变化；多世循环经过真人测试 |
| 手机体验 | 5键导航、详情折叠、动效可跳过 | 320–430px真机触控、离线恢复/十连/战斗长期运行不卡顿 |
| 工程可信度 | 随机种子可复现、Schema隔离、CI自动测试 | 战斗/经济/概率/跨世/恢复压力测试，浏览器存档兼容与高阶大数安全 |

**对“全部9分”的正确口径**：先完成各项不可缺少的核心体验，再用匿名真人试玩、会话完成率、下一次主动打开的意愿和跨世自愿重玩判断。此文不把自动测试50/50通过等同于玩家体验9/10。

## I. 横屏战斗中控台重构方案 v1（**待用户确认，仅设计，未实装**）

> 提案日期 2026-10-20。参考用户提供的 Melvor Idle 战斗截屏的**信息组织方式**，不复刻其美术、图标或既有IP。主方向：PC 三栏、手机横屏双战斗栏 + 抽屉导航，保留无数字 Lv 的修仙世界与“战斗产基础资源、养成抽卡获得”的原则。**本节不是当前代码已完成的功能清单。**

### I.1 设计目标 / 不做什么

玩家打开游戏后应一眼看懂：自己在打谁、双方HP与攻击进度、自己的主要养成数值、装备与功法、预计掉落资源，以及怎样更换地图或刷怪目标。只需展开详情即可追溯具体计算和克制，不需要跨多个系统寻找当下战斗信息。

本期优先重排 **界面/输入/数据展示**，不顺便改卡池概率、地图指数或永久遗物，不新增无依据的“敌人装备掉落”。修仙装备系统须保持“通过卡包获得构筑”，未经重新确认不得改变这一核心原则。现行 v0.9 只有功法和灵宠装配，**不存在已完成的装备库存、装备属性结算或装备掉落**。

### I.2 响应式布局：按可用宽度，而不是只看设备型号

桌面宽屏 ≥1100 CSS px：左侧固定系统导航约 200–230 px；其余空间玩家区占约43%、敌方区57%。中等宽度 800–1099 px：侧栏可缩为56–64 px图标带，其余仍为两栏。手机横屏通常 667–930 CSS px：左导航默认隐藏，以左侧按钮或从屏幕左边缘起始的滑动唤出；主体玩家区约46%、敌方区54%。若屏幕宽度/高度不足（例如窄屏分屏模式），改成**“我方/敌方”双页签**，不能为了保持三栏让属性文字缩到不可读。

### I.3 玩家区（左侧主战斗栏）

- 固定头部：境界、当前功法/流派、HP 现值/上限与平滑血条、出手冷却条（明确显示秒数）。
- 精简参数：攻击、防御、气血、命中率、闪避、当前攻速、承伤减免；其余加成按既有 \`details.mjs\` 默认折叠。
- 视觉主模块：**6个候选装备槽位**（武器/头冠/法衣/足履/饰物/护符），先可显示空槽与“待解锁”，但未开发的槽位不能伪造生效数值。点击开启背包抽屉，列表可比较装前/装后属性。
- 现有功法与灵宠仍独立生效，展示当前装备名称、技能与战斗活动状态；不要把“功法”硬迁移成传统武器数据。
- 后续状态：护盾、暴击、异常状态等只有**战斗引擎真实支持**才显示生效标识；没有实现的属性用“规划中”而不是可交互假按钮。

### I.4 敌人区（右侧战斗栏）

- 面板：攻击、防御、命中/闪避、特殊能力，默认给出简短描述；详细概率、伤害减免等展开显示。守卫2波、Boss3波展示阶段计数，并保留跨波气血状态。
- 操作：当前关普通妖怪「均衡/灵石优先/修为优先」，手动挑战守卫、Boss（未解锁禁用并说明条件）、自动刷小怪/自动冲关；首通与重复击杀奖励必须如实区分。
- 资源预览：只显示引擎确实会掉的灵石和修为及预计效率；**装备掉落若未正式设计，不在这里显示虚假的装备掉率或承诺**。

### I.5 地图与选关交互

左侧导航抽屉 →「地图」→ 已解锁地图列表 → 区域详情和关卡节点（1–7守卫，8为该图Boss）→ 当前可选的小怪。未解锁地图灰显并注明条件；已通关地区可浏览，但**不得改变既定的当前关刷怪积累与Boss进图规则**。在地图页展开小怪种类与资源倾向，返回战斗区应保留当前活动状态；切换正在挂机的目标时，必须先结算旧目标已经经过的时间，再切换目标，杜绝时间套利。

### I.6 装备系统 MVP：真实数据与获得来源

**建议来源为新装备抽卡包**（例如「器物秘匣」，可以作为第8类包，具体名称、解锁节点与价格待审批）。此决策优先维持已经反复确认的游戏主轴；**本方案不默认把装备改成小怪/守卫直接掉落**。若用户选择“战斗可掉装备”，应先修改核心原则与GDD，再实施，而非开发者私自决定。

- 先提供6个槽的**可视位置**，MVP首批仅开放武器/法衣/饰品/护符4个可实际装备的槽位，其余头冠/足履可标「后续开放」，避免一次铺6套随机词缀。
- \`EquipmentDefinition\`：\`id, name, slot, rarity, flatAttack?, flatHp?, flatDefense?, speedPct?, tags?, unlockAt?\`。
- \`OwnedEquipment\`：来自随机抽卡的实例 \`instanceId, definitionId, acquiredAtDraw\`；\`equipped[slot]\`指向实例ID；不能仅通过传入任意装备ID伪造持有。重复卡未来可作为升星/洗练素材，但本期不要顺带做完整强化系统。
- \`RunState\`存放本世持有与装配；轮回重置当世装备，\`MetaState\`只保留正式定义的永久奖励；更改Schema必须备份、迁移、升级旧存档的兼容测试。
- 属性只从**唯一一条结算路径**进入 \`heroStats\` 和 \`combatSnapshot\`，界面读取选择器，不能在DOM中再次拼算。首版仅攻击/HP/防御/攻速四类，暴击/元素属性暂不加入。
- 装配比较：装备前/后攻击、HP、防御、出手秒数的变化；单次仅装备一个槽位；背包浏览/筛选/取消/替换都必须能在手机横屏完成。

### I.7 战斗时间与动画契约

当前 \`src/v8/combat-depth.mjs\` 已可纯函数返回命中/未命中、伤害、回复、多波日志；\`ui.mjs\`以压缩时间播放战报，而 \`idle.mjs\`按另一层挂机间隔结算。**这一差异必须明示，不能把UI的攻速条当作已经实现“完整实时战斗时钟”。**

界面第一阶段：仍以现有引擎为真值，**先安全地播放已经结算的日志**，不改胜负、掉落、概率、随机种子。第二阶段再统一在线/离线/手动的战斗活动时间（采用统一的纯事件时间线/战斗序列；同一场不能双重结算），攻速条才真正与战斗引擎匹配。动作时间与奖励落盘必须分离，切到后台、关闭动画或低帧率设备不改变发奖结果。

### I.10 决策点（确认方案后才动代码）

1. 主玩法按**横屏优先、桌面三栏、手机横屏双栏 + 侧抽屉**；竖屏轻提示加精简兜底，而非强制全屏方向锁定。

3. 优先上线 **UI-0 + UI-1**，让用户对真实可玩效果验收后，再推进装备数值（EQ-1）和时间时钟（CLOCK-1），避免一轮同时重写规则、渲染与存档。
